### Added
- **§37.5 — the profile wizard covers weather thresholds.** Wizard screen 15 (Safety) now offers the §35.1 weather-threshold settings inline — turn the weather-station reaction on and set wind (km/h), humidity (%), and dew-delta (°C) limits during first-run setup instead of hunting for them in Settings afterwards. Blank fields keep the profile defaults; the full editor remains in Settings → Safety → Policies.
- **§35.5 — the safety alarm is audible now.** When the daemon reports UNSAFE (safety monitor, weather threshold, or an emergency stop), WILMA pops a safety modal immediately and — after a configurable silent delay (default 5 s, so a user at the screen can silence it before it rings) — loops an alarm tone at full volume until silenced or conditions clear. Three bundled tones (two-tone siren, urgent beeps, rising chime) and the delay are device-local knobs under **Settings → Session → Notifications**, behind the existing "Sound alert" master toggle; the daemon fires the event *before* its reaction runs, so the alarm and the park happen in parallel.
- **§44 — cap the backup stream's bandwidth.** Settings → Session → Storage gains "Bandwidth cap (Mbps, 0 = unlimited)": the real-time backup's average download rate stays under your cap — each frame still moves at link speed, then the puller waits before the next one — on top of the existing pause while an exposure is downloading. The status line now also reports the link speed measured on the session's first pull ("link ≈ N Mbps") so you can pick a sensible number. The cap persists with the toggle and folder.
- **§44 — the backup stream is visible at a glance.** A live chip on WILMA's bottom status bar shows the real-time backup's pulse from any tab — pending count while frames drain, "up to date" when the mirror is current, and an attention state (with the reason in its tooltip) when something needs you; it stays hidden entirely on rigs that never enabled the stream. In the Image Library, each frame now carries a small cloud badge — filled when that frame is confirmed stored on your desktop, outlined while its backup is still pending — again only when a backup stream is configured, so a missing badge never falsely reads as "unprotected".
- **§35.1 — weather-threshold reactions.** With an ObservingConditions weather station connected, the daemon can now react to the numbers, not just a boolean safety monitor: turn on **Settings → Safety → Policies → "React to weather-station thresholds"** and set wind (km/h — sustained or gust, whichever is worse), humidity (%), and dew-delta (°C above dew point) limits. A breached threshold makes conditions unsafe through the exact same machinery as the safety monitor — your "when conditions turn unsafe" action runs, the alert names the tripped threshold ("wind 54 km/h over the 36 km/h limit"), and auto-resume waits until *every* source (monitor and weather) reads safe. Off by default so an upgraded rig never surprise-parks; a sensor your station doesn't report is simply skipped.
- **§35.3 — the emergency stop.** A persistent red **Emergency Stop** button now lives on WILMA's bottom status bar, one tap away from every tab. After a confirmation, the daemon runs the stop ladder behind the new `POST /api/v1/server/emergency-stop`: abort the running sequence first (so nothing starts a fresh exposure behind the stop), abort the in-flight exposure, stop guiding, park the mount, and switch the flat panel light off. Every step is best-effort — one dead device never blocks the rest — and the result is reported honestly in WILMA (an unreachable mount says "MOUNT NOT REACHED — verify it manually", never pretends it parked). The `safety.emergency_stop` event fires before the ladder so clients can alarm while the daemon works; a double-press mid-stop is ignored.
- **§48 — the "capture calibration tonight?" prompt arrives in WILMA (client half).** Starting a sequence (with the profile default set to "ask") now pops a dialog in WILMA: panel flats at end, sky flats at twilight, or not tonight — with a "remember my choice" checkbox that persists the answer as your profile default. The new **Settings → Session → Calibration** panel lets you view or change that default any time (ask / panel / sky / never), ⌘K-searchable with a full help entry. A prompt from a newer run replaces a stale unanswered dialog so the answer always binds to the run that's actually asking; dismissing the dialog is the same safe "not tonight".
- **§44 — real-time frame backup arrives in WILMA (client half).** Settings → Session → Storage gains "Stream new frames to this device": your desktop claims the daemon's backup-stream slot and mirrors every captured FITS as the night runs — downloaded, SHA-256-verified, written atomically under your backup folder as `<server>/<session>/<frame>.fits`, and confirmed back to the daemon. New frames trigger a pull within seconds (the `frame.complete` event nudges the poll), transfers hold while an exposure is downloading from the camera, a crashed desktop resumes exactly where it left off, and if another desktop takes the slot the panel says who has it. The status line shows pending/synced counts live; both settings are ⌘K-searchable with full help entries. The toggle and folder persist across app restarts — a persisted-on stream resumes on its own at launch — a denied claim keeps retrying until the slot frees up, and disk trouble (full or unwritable backup folder) surfaces in the panel instead of retrying silently. (Footer progress chip, per-frame sync icons in the library, and the configurable bandwidth cap are tracked follow-ups.)
- **§48 — "capture calibration tonight?" is enforced end-to-end (server half).** Starting a sequence now consults your profile's new calibration capture default: "ask" (the default) emits the `sequence.auto_flats_prompt` event for WILMA's dialog and the answer rides `POST /api/v1/sequences/{id}/auto-flats-decision` ("remember my preference" persists it); "panel at end" / "sky at twilight" auto-decide silently; "never" stays quiet. When a run **completes** with a yes-answer, the daemon generates the §39.5 matching-flats sequence from that run's own session — every filter replaying tonight's focus, gain, and offset — and for "panel at end" **starts it immediately** with a light-your-panel notification; "sky at twilight" generates it ready-to-run and says so honestly (automated twilight timing is a tracked follow-up). Aborted or stopped runs never trigger flats — ending the night on your terms means exactly that. The WILMA prompt dialog + Settings → Calibration panel are the client follow-up slice.
- **§44 — the real-time backup stream is real (server half).** A desktop WILMA can now claim the daemon's single backup-stream slot (`POST /api/v1/server/backup-stream/claim` — the same hostname re-claims after a crash; a different desktop takes over only after the holder goes silent), poll the pending queue of catalogued frames oldest-first (each entry carrying a SHA-256, computed lazily and cached so pre-existing frames backfill automatically), pull the FITS bytes via the existing frame-download endpoint, and ack each verified file — building a continuously-updating mirror of the night's frames so a mid-session USB failure costs at most the in-flight exposure. Unverified acks are refused (the frame stays queued), a takeover re-queues everything for the new desktop (each target gets a complete mirror), and `GET /backup-stream/status` reports pending/synced/queue-bytes. The WILMA client half (Settings → Backup toggle, footer progress, per-frame sync icons) is the follow-up slice.
- **§63.3 — a wedged guider can no longer go unnoticed, and a recovered one reconnects itself.** While connected, the daemon now actively pings the guider (`get_app_state` on a fresh RPC connection — every 2 s while guiding, 10 s otherwise); three consecutive failures declare the daemon down even when its socket is still open, triggering the same recovery + §42.2 sequence reaction as a real disconnect. And when the §63.3 process recovery brings the guider service back, ARA now **reconnects automatically** within your "guider retry timeout" window (Settings → Safety → Policies), re-pushing the guiding settings on connect and posting a "reconnected — resume your run when ready" notification; if it can't reconnect in time it says so and leaves the manual path. A user connect/disconnect always supersedes the automatic one.
- **§42.2 — losing the guider mid-sequence now enforces your "on guider lost" policy.** When the guider connection drops while a sequence is running, the daemon reacts immediately per Settings → Safety → Policies: pause the run at the current instruction (the default — no more unguided frames burning sky time; resume after reconnecting), skip the current target, or abort the sequence — until now the setting existed but a mid-guiding crash was notify-only. The §63.3 automatic process recovery still runs alongside; the sequence action posts its own Critical notification and a `guider.fault_action_taken` event, and fires once per disconnect episode (a fresh connect re-arms it). With nothing running, the crash notification alone is posted — no noise.
- **§35 — the daemon now reacts when your safety monitor says unsafe.** With an Alpaca SafetyMonitor connected, a safe→unsafe report now triggers your profile's "when conditions turn unsafe" policy within the 10-second poll: pause the sequence at the current instruction + stop guiding + park the mount (the default), park only, abort + park, or notify only — until now the setting existed but nothing enforced it. WILMA receives `safety.unsafe` before the action (so the alarm can sound while the daemon reacts) and `safety.action_taken` after. With "auto-resume when safe" on, conditions staying clear for your configured delay unpark the mount, restore tracking, and resume the paused run — with a notification reminding you to verify pointing if your sequence doesn't re-center. A run paused *awaiting your attention* (a failed meridian flip) is never auto-resumed, and the safety engine's automated actions never count as "the user is back" for the §58.12 unattended-shutdown countdown.
- **§37.6 — the setup wizard pre-checks the recommended sky data.** The sky-data step now arrives with the curated star + deep-sky catalogs already ticked (badged "Recommended") so a fresh profile gets the packages the planner and atlas actually use — untick anything you don't want; your own picks are never overridden.
- **§25.5.5 — camera readout modes and a visible cooling target.** The camera panel gains a readout-mode picker (the driver's own mode list; switching re-reads the per-mode sensor electronics), shows "Cooling to −10.0 °C" next to the actual sensor temperature while the cooler runs, and renders asymmetric pixel pitches ("3.76 × 3.80 μm") when a sensor reports them.
- **§25.5.5 — the dome panel grows the rest of its controls.** Find home, Set park here (store the current position as the park position), Sync (re-label the current physical azimuth), and a Stop button that stays enabled while the dome is moving — each shown only when the connected dome reports the matching capability. Backed by four new daemon endpoints (`/equipment/dome/findhome`, `/abort`, `/setpark`, `/sync`).
- **§36 — sky-data downloads wind down cleanly on daemon stop.** A graceful daemon shutdown now cancels any in-flight sky-data download and waits for it to finish tearing down, so its temp files are reclaimed immediately and the client sees a proper "cancelled" event — instead of the worker being abandoned mid-transfer and its scratch directories waiting for the next boot's sweep.
- **§43 — backups no longer pile up forever.** The daemon now keeps the newest N configuration backups (Settings → Session → Storage → "Keep backup snapshots", default 20; set 0 to keep everything) and prunes older snapshots automatically after each new backup. Backups are tiny, so 20 keeps weeks of history at negligible cost — but until now the folder grew without bound.
- **§63.6 — guider calibration builds go live in WILMA.** The guider calibration dialog now shows dark-library and defect-map builds as they run (driven by the daemon's WebSocket events): an unmistakable "Building — keep the scope covered" state while the capture runs, an automatic status refresh when it finishes, and the daemon's error message if it fails. Every build now asks you to confirm the scope is covered first — light on the sensor silently corrupts a dark build. A build rejected because another one is running now says exactly that (instead of a generic failure), as does a disconnected guider. The WebSocket protocol also gained a `?ws_version=` query fallback so future browser clients can connect (browsers can't set the version header).
- **§43 — restore a backup from another daemon.** `POST /api/v1/backup/restore-zip` now accepts a remote http(s) `backup_source_url` (for example another ARA daemon's snapshot-download URL on your LAN): the daemon downloads the archive, verifies it against the request's new required `sha256` field before anything touches your live config, and then restores it exactly like a local snapshot — same atomic swap, same progress polling. Local snapshot restores are unchanged. The WILMA screen for picking a remote daemon's snapshot comes in a later slice; the server API is ready now.
- **§51 — the diagnostics pill can no longer get stuck on a reconnect.** The daemon now sends the full set of currently-open diagnostic issues to every WebSocket connection right after it's accepted (`diagnostics.snapshot`), and WILMA resyncs its health roll-up from it. Previously, if the link dropped at the exact moment an issue cleared, the pill stayed amber/red until you switched servers; now it heals on the next reconnect automatically.
- **§58.12 — unattended-failure graceful shutdown.** When a run pauses awaiting your attention (a failed meridian flip at 3am) and nobody responds within the configured window (`safety.unattended_shutdown_wait_minutes`, default 10; `safety.unattended_shutdown_enabled` to opt out), the daemon puts the rig to bed: guider stopped, mount parked (or tracking stopped), filter wheel/focuser/rotator/flat panel disconnected, cooler warmed gently at your profile's ramp rate, camera disconnected last, and a summary notification posted for the morning. Dismissing the alarm notification, any sequence/equipment command, reconnecting, or simply opening WILMA counts as "you're back" and cancels the countdown — background status polling never does. The run stays paused and resumable.
- **§58.12 — unattended-shutdown dials in WILMA.** Settings → Safety → Policies gains "Unattended shutdown after failure" (default on) and its wait-minutes field, mapped to the daemon's new profile fields and searchable via ⌘K ("shutdown", "countdown", "battery"). The Load-sequence badge for a run that's paused awaiting you now reads "needs attention" instead of the raw state name.
- **§58.12 — WILMA understands the new "paused — needs your attention" run state.** When the daemon suspends a run after an urgent failure (a failed meridian flip with the mount in safe rest), the sequencer toolbar now shows "Paused — needs your attention" with Resume ready to release it (the flip is re-attempted on resume), and the Load dialog badges the run in red instead of the calm paused blue. Older daemons are unaffected.
- **§58.12 — a failed meridian flip pauses the run instead of killing it.** When the flip executor gives up (any §58.9 layer), the sequence now suspends in a new `pausedawaitinguser` state — resumable — rather than ending as `Failed`: the mount is already in safe rest, no further frame fires, and the existing Resume re-attempts the flip (flight check included) once you've sorted the rig out. Abort/stop still work while suspended, and the sequence file stays protected from edits/deletes like any live run. This is the state the upcoming unattended-shutdown countdown keys off.
- **§36 — enter your skyline in WILMA (custom horizon editor).** Settings → Safety → Site now embeds a vertex editor under the "use custom horizon" toggle: add azimuth/altitude points for your trees and rooftops, and Save persists them with the site preferences (the daemon sorts and validates, and the panel adopts its canonical echo). Searchable via ⌘K ("skyline", "obstruction", "horizon").
- **§36 — the custom terrain horizon is real (daemon half).** The profile stores your measured skyline (azimuth/altitude points, `GET/PUT /api/v1/profile/custom-horizon`), and with "use custom horizon" on it now actually applies: Tonight's Sky visibility windows respect the trees and rooftops per compass direction instead of one flat altitude, and the planning chart's horizon overlay draws the real skyline shape. Skylines are stripped from shared profiles (terrain fingerprints a location). The WILMA editor screen follows in a separate PR.
- **§40 — each sequence run gets its own session in the image library.** Frames captured by a run now group under a session created for that run (named after its target, per the existing derivation), instead of piling into the same "manual capture" bucket as ad-hoc snapshots — so the library and §50 stats finally reflect imaging runs. `session.started`/`session.ended` events accompany the run on the WebSocket.
- **§60.9 — equipment chips react to connection changes instantly.** WILMA's equipment providers now refresh the moment the daemon publishes an `equipment.state_changed` event, instead of waiting for the next poll tick (up to 15 s) — and the Switch panel, which had no background poll at all, now notices daemon-side switch transitions without a manual refresh. Polling stays as a fallback for daemons predating the events.
- **§60.9 — equipment connection events finally flow over the WebSocket.** Every device service (camera, mount, focuser, filter wheel, rotator, dome, switch, flat panel, weather, safety monitor) now publishes `equipment.state_changed` on every connection-state transition, plus `equipment.connected` / `equipment.disconnected` / `equipment.connection_failed` at the notable moments — these event types were in the catalog from day one but nothing emitted them, so clients had to poll to notice a device appearing, vanishing, or failing.
- **§38 — the daemon refuses to edit or delete a sequence with an active run.** `PATCH`/`DELETE /api/v1/sequences/{id}` now return 409 Conflict while that sequence's run is Starting/Running/Paused/Aborting, instead of rewriting or deleting the file out from under the live executor. Any client (or curl) is covered — the invariant lives in the daemon now, not just in WILMA's pre-flight probes.
- **§27 — single-client policy in WILMA (client half).** WILMA now claims the control slot on connect (and silently re-claims its own session after a Wi-Fi blip), answers the daemon's takeover requests with an "X wants to connect — Allow / Keep me connected" modal, and treats WebSocket close 4004 as "Session transferred": a modal explains another client took control (the running sequence is unaffected) and reconnecting is an explicit button, never automatic. Denied or unavailable claims degrade gracefully — the live event stream keeps working against older daemons and while another client holds control.
- **§27 — single-client policy: connect handshake + 4004 takeover (server).** The daemon now serves one controlling client at a time: `POST /api/v1/server/connect` claims the slot (a live holder gets a `connection.request` modal over its WebSocket and can allow or reject the takeover; a holder silent for 60 s is swept automatically), `POST /api/v1/server/disconnect` releases it, and `GET /api/v1/server/session` shows who is connected. A displaced client's WebSocket is closed with code 4004. Pre-§27 clients that never call `connect` are unaffected — the event stream and REST keep working unchanged.

### Fixed
- **§60.9 — reconnecting after a daemon restart is up to 3× snappier.** The WebSocket retry backoff now caps at 10 s instead of 30 s, so once the server is back the client notices within seconds instead of potentially half a minute.
- **§36 — connecting-to-no-server feedback is consistent across Planning.** "Add to Sequence" from the target action bar and Tonight's Sky rows now shows the same "Connect to a server before creating a run" message the framing overlay already showed (previously those two failed silently), and all three surfaces share one set of outcome messages.
- **§37 — older saved profiles no longer ship `null` sections on the wire.** A profile saved before newer settings sections existed (camera electronics, optics, filter set, …) used to return those sections as `null` from `GET /api/v1/profiles/{id}` and in profile-share exports; every snapshot read now back-fills missing sections with defaults at the source, matching what the active-profile store already did.
- **§28 — unknown sensor temperature is recorded honestly.** A camera that reports no CCD temperature now records "unknown" instead of a fabricated 0.0°C (existing databases upgrade in place; dark-matching for uncooled cameras keeps working across old and new recordings), and exports/views show a blank instead of a fake reading.
