- **§59 — autofocus actually focuses now.** The live V-curve sweep is built: the daemon steps your focuser through the configured sweep (all in one direction, so mechanical backlash biases every sample identically), measures star HFR at each position through the same camera path real captures use (probe frames are never saved to your catalog), fits the focus curve, and moves to the fitted best — restoring your starting position if anything fails, per your autofocus settings. This makes three things real at once: the **Run Autofocus** step in imported NINA plans, autofocus-after-N-exposures triggers, and the meridian flip's **re-focus after flip** (a failed re-focus logs and continues — it never aborts your night). A sweep that can't trust its data — too few stars, a flat curve, a best-focus estimate outside the sweep — fails loudly instead of guessing.
- **§38 — imported "Center and Rotate" steps now actually centre the target.** A NINA plan's `CenterAndRotate` executes for real: the daemon runs its plate-solve centering loop (capture → solve → sync → re-slew until within your profile's threshold) on the step's own coordinates, and a centre that doesn't converge fails the step loudly instead of quietly ruining every following frame. With a rotator connected the step still fails loudly (rotation isn't wired yet — better than silently mis-framing a rotator rig); without one, the position angle is preserved in the plan but skipped, exactly as NINA behaves without a rotator.

### Changed
- **Licensing — the WILMA client is now AGPL-3.0-or-later; the daemon stays MPL-2.0.** The repo carries a per-directory license split: `client/openastroara_client/` gains its own `LICENSE` (GNU AGPL v3 or later), while the server/daemon and everything else remain under the Mozilla Public License 2.0 (required by the NINA-derived code's lineage, which is unchanged). The client is wholly original work, and AGPL's network clause keeps derived clients open even when they're served from a device rather than shipped. The two halves communicate over REST/WebSocket as separate programs, so the licenses apply independently — see `NOTICE.md` and `design/PORT_DECISIONS.md` (2026-07-01). Existing MPL-2.0 revisions remain MPL at those revisions; this applies going forward.
- **§36.8 — Tonight's Sky inclusion changed from "up right now" to "has a dark window tonight".** Targets are now listed when they have any real dark window in the night (so not-yet-risen ones appear), and ranked by the new equipment-aware score instead of current altitude. A target with no dark window tonight is the only thing dropped.
- **§36 — the planetarium now renders in the platform's *native* webview; CEF was removed entirely.** The Stellarium planetarium renders through the OS web engine via `webview_all` — **WKWebView** (macOS/iOS), **WebView2** (Windows), **WebKitGTK** (Linux), **System WebView** (Android) — replacing the bundled CEF/Chromium (`webview_cef`). CEF was compiled in and registered on every platform regardless of build flags; it froze under sustained offscreen-render load on macOS, and on Linux its `libGL`/CEF init broke Flutter's GTK OpenGL context outright (the whole app failed to render — a stock Flutter app on the same machine renders fine). Dropping it collapses the renderer to one code path, removes the multi-process CEF helper scaffolding + the hundreds-of-MB Chromium download from the build, and lets the macOS Hardened-Runtime entitlements shed the CEF-only JIT/executable-memory grants. It also unblocks Linux and makes Android/iOS feasible (CEF is desktop-only). The dead Aladin atlas widget (long superseded by the Stellarium engine) was removed in the same pass.
- **§36 — planetarium pan/zoom is now native; on-screen pads removed.** With the webview giving proper trackpad/mouse input (scroll to zoom, drag to pan), the corner direction pad and the +/- zoom cluster were redundant and were removed for a cleaner full-bleed sky. The bottom "GoTo here" reticle was also removed (clicking objects directly replaces it). The Flutter DEBUG ribbon is also hidden (it overlapped the connect screen's Rescan action).
- **Equipment panels: clearer copy + a tidier Filter Wheel.** Removed the internal spec-section labels that leaked into the UI (the "§52.1 connection lifecycle" hint under Auto-connect on the Camera/Mount panels, and the "§37.11"/"§29.3.2" references). The Focuser panel's dead autofocus placeholder rows are gone — it now links to the real, editable settings under **Imaging → Autofocus**. On the **Filter Wheel**, each live slot now shows its **driver slot number** (0-indexed, matching "Current filter (slot N)"); the focus-offset readout is relabelled "focus offset" and hidden entirely when every slot reports 0 (so wheels like the ZWO EFW don't show a column of zeros); and the local **"Slot labels (for sequences)"** section is hidden while a wheel is connected (its driver names are authoritative) and shown only for offline sequence authoring.
- **§36 — the macOS minimum is now 12.0 (Monterey); Catalina (10.15) and Big Sur (11.x) are no longer supported.** The §36 Sky Atlas moved to CEF 149, whose framework requires a macOS 12.0 deployment target — so the app's `MACOSX_DEPLOYMENT_TARGET` was raised from 10.15 to 12.0. Users on 10.15/11.x can no longer run the desktop client.

### Fixed
- **Equipment status no longer shows stale "connected" green after the server drops.** The top-bar device chips (CAM/FW/FOC/MOUNT/ROT/GUIDE/FLAT/SW/WX/SAFE/DOME) and the device panels in Options mapped each device's *last-known* status straight to the dot/layout, so when the server was killed or became unreachable they kept rendering a false green long after the app had lost contact. A new `serverLinkUpProvider` (true only while the live server link is fully connected) now gates them: link down → chips go grey (disconnected) and each device panel shows a clear "Server disconnected — device status is unavailable" state instead of stale connect/disconnect controls. They repopulate with real status the moment the link is back.
- **§60.9 — the live server WebSocket no longer drops every fresh connection (status was stuck "Reconnecting").** Two compounding bugs: (1) the daemon's resume phase enforced its 5-second "send a resume request" window by cancelling its `ReceiveAsync`, but a cancelled `WebSocket.ReceiveAsync` *aborts* the socket (close 1006) — so any client that stayed silent past 5s (i.e. every fresh subscriber) was dropped, then reconnected and dropped again, forever. The resume phase now races the receive against a delay *without* cancelling it, handing the still-pending receive to the main loop on timeout, so a silent client stays connected as a fresh subscription. (2) The client only sent a resume frame on a *re*connect; a fresh connect sent nothing, so it tripped (1) every time. The client now always sends a resume frame first (token `"0"` when fresh), which also draws a resume-response back that flips the link to connected. The status chip is also relabelled to the explicit client↔server link — **Server connecting… / connected / reconnecting… / disconnected** — so it can't be mistaken for a device/camera state.
- **Mount manual-control: a held direction button now stops if the mount goes busy.** On the §37.5 direction pad, if the mount became busy from another source (a sequence step, a GoTo) while a direction was physically held, the button greyed out but the axis kept moving until the user released. The press-and-hold button now dispatches the stop on the disable transition (not only on release/teardown), so a held nudge halts as soon as the control disables. (Stop / AbortSlew remained the deadman regardless.)
- **Mount Park now works (it was silently failing).** Two issues: (1) the Park button POSTs `/equipment/mount/park` with no body, but the endpoint required a `[FromBody] ParkRequestDto`, so model binding rejected the bodyless request (400/415) and the mount never parked — the body is now optional (its only field is an optional reason, defaults to null). (2) Some mounts (e.g. iOptron) won't execute a park from a stationary state, so the daemon now enables tracking before issuing Park — exactly as ASCOM ConformU/NINA do. (Unpark/Stop were unaffected; Slew always sends RA/Dec.) Note: a mount that parks to a position *other* than its home/zero may still no-op a park issued from the home position — slew it to a normal pointing position first (see the new Manual control GoTo).
- **Every device panel now offers Reconnect again after you disconnect it.** The device services keep the last device after a disconnect and report it with `state == disconnected` (a non-null status GET, not a 404), but the shared `EquipmentConnectionCard` only showed its disconnected layout — the one carrying the **Reconnect** + **Connect…** buttons — when the status was null. So a device disconnected during the session rendered the *connected* layout (just a Disconnect button), with no way to reconnect it short of re-discovering via Connect…. The card now treats a `disconnected` status the same as a missing one, so Reconnect reappears the moment you disconnect — across all nine equipment panels.
- **The top-bar FLAT chip now actually turns green when you connect a flat panel.** The chip was wired to the live flat-panel provider, but the Flat Panel settings panel was the one device panel that still connected through the old wizard-style row (`AlpacaDeviceRow` on `equipmentConnectionProvider`) instead of through that provider — so connecting a flat never told the chip's provider, which had stopped polling after its initial "disconnected" read, and the dot stayed grey. The Flat Panel panel now uses the same shared `EquipmentConnectionCard` as the other eight device panels (connect/disconnect/reconnect on the live `flatPanelProvider`), with a live cover/light readout; connecting — or turning the calibrator light on — now lights the chip and shows the state in the panel. This also gives the flat panel the same disconnected-state **Reconnect** affordance as every other device.
- **§52.1 — switches now auto-reconnect on boot like the rest of your gear.** Switch was the one device type the daemon never re-established on startup: the selection store only remembered one device per type (so a multi-switch rig couldn't round-trip), there was no Switch case in the auto-connect service, and no Switch auto-connect-on-boot toggle. Now every connected switch is remembered independently (by its Alpaca device number), the auto-connect service reconnects them all on boot, and the Switch panel has an **Auto-connect on boot** toggle (default on). So after a daemon/rig restart your switches come back without manual reconnection — matching camera/mount/focuser/etc.
- **The top-bar FLAT (cover calibrator / light panel) chip now shows live status.** It was a hardcoded placeholder that always rendered disconnected — so a connected light panel never lit up at the top. It now watches the flat-panel status provider like the other equipment chips: green when connected, amber while the cover is moving, and routes to the Flat Panel settings panel on tap. (The daemon already fully supported CoverCalibrator/flat devices — discovery, connect, control, auto-connect; only the client chip was static.)
- **§36 — the macOS client now actually runs CEF 149 multi-process, and the native macOS build is no longer broken.** The preceding Sky Atlas change raised the client to **C++20** and documented CEF 149, but left the `webview_cef` submodule pinned at **CEF 130** — whose `libcef_dll_wrapper` doesn't provide the wide-char stream operators (`operator<<(ostream&, char16_t/wchar_t const*)`) the C++20 build links against, so `flutter build macos` failed with *undefined symbols* (client CI runs `analyze + test` only and never compiles the native Runner, so the break slipped through the gate). The submodule is bumped to the CEF 149 multi-process build, and the macOS Runner now embeds the **full five-helper set** (base + `GPU`/`Renderer`/`Plugin`/`Alerts`) Chromium-on-macOS requires — a single helper made the GPU subprocess abort with `gpu_process_host error_code=1003`. All five helpers sign with the committed `Runner/Helper.entitlements`, and `macos/CEF_HELPER.md` is reconciled to the multi-process model. Verified on-device: the client launches multi-process (`gpu-process` + `renderer` + `utility`) and Aladin renders.
- **§36 — the Planning Sky Atlas renders on CEF 149 instead of crashing/blanking.** Moved the embedded Aladin webview to CEF 149 with software-WebGL offscreen rendering and lifecycle fixes: the bootstrap document is written to a temp file and loaded via a short `file://` URL (a self-contained `data:` URL exceeded Chromium's ~2 MB max-URL length once the ~1.9 MB engine is inlined, so CEF silently rejected the navigation and left the atlas blank); the tab is kept alive in an `IndexedStack` so a rebuild can't tear down the OSR browser mid-flight; and CEF is shut down cleanly on app exit (bounded by a timeout so a hung teardown can't wedge the quit). The macOS App Sandbox is disabled on the host — CEF 149's multi-process Mach rendezvous registers a PID-suffixed *global* bootstrap name that the sandbox denies, aborting `CefInitialize`; this is acceptable for the Developer-ID-distributed desktop control app (not Mac App Store) and documented in `macos/CEF_HELPER.md`.
- **§38 — a loaded/imported sequence now wires up its parent chain, so run-engine features that walk to the root work.** A serialized sequence body stores each node's `Parent` as null; on deserialize the parent links weren't re-established, so a running instruction couldn't find its root container — breaking running-item tracking (and therefore skip-current). `SequenceContainer`'s `[OnDeserialized]` hook now re-parents its children (Newtonsoft fires it bottom-up, so the whole tree is wired by the time the root's hook runs).

- **§38 — imported autofocus / center-and-rotate steps now render as first-class blocks in the editor.** Building on the server-side port (#594), the client catalog now knows `RunAutofocus`, `CenterAndRotate` (coordinates + position-angle editable) and the `AutofocusAfterExposures` trigger, so imported plans containing them show real labels/icons instead of generic fallbacks.
- **§38 — autofocus, center-and-rotate and autofocus-after-N-exposures now import from NINA too.** `RunAutofocus`, `CenterAndRotate` (coordinates + rotation angle preserved) and the `AutofocusAfterExposures` trigger were the last high-frequency NINA `$type`s still dropped on import; they now resolve to first-class ported types. (Their run-engine execution into the §59 autofocus / §28 centering services is a follow-up — for now an executed step fails loudly rather than silently skipping focus/centering.)
- **§38 — imported NINA targets, Smart Exposures and dither triggers now render as first-class blocks in the sequence editor.** Building on the import + type-normalization fixes, the client catalog now knows `DeepSkyObjectContainer` (a target block, labelled by its target name — e.g. "T Cas" — rather than a generic container), `SmartExposure` (NINA's per-filter imaging block), and the `DitherAfterExposures` trigger (with its after-N-exposures cadence editable). - **§38 — an imported NINA sequence now renders with real instruction names in the editor, not generic placeholders.** The importer persisted the raw NINA body, so every node kept its original `NINA.Sequencer.*` type name — but the editor/catalog identify instructions by the daemon's own `OpenAstroAra.Sequencer.*` names, so an imported sequence showed a tree of unlabeled rows. Import now rewrites each `$type` to its canonical OpenAstroAra form (only when it resolves to a real type — an unsupported instruction is left exactly as-is, with all of its data, and reported in the import warnings), so imported sequences read identically to ones built in the editor. The raw NINA upload is still kept verbatim as an audit copy.
- **§38 — importing a real NINA sequence no longer drops the bulk of the plan.** NINA Advanced Sequencer exports are built almost entirely from three `$type`s the daemon didn't recognize — `SmartExposure` (the per-filter imaging block), `DeepSkyObjectContainer` (the per-target block carrying the target name + coordinates) and the `DitherAfterExposures` trigger — so every one degraded to an `Unknown*` placeholder on import and the imported sequence lost its targets and exposures (a 2.8 MB / 228-target file imported as a near-empty tree). All three are now ported as first-class types: a target imports with its name, framing rotation and RA/Dec intact; a Smart Exposure keeps its filter switch, exposure-count loop and dither cadence; and the tree round-trips back to NINA JSON unchanged. (Faithful port — `SmartExposure`/`DeepSkyObjectContainer` subclass the existing `SequentialContainer`, so they also execute as ordinary nested containers.)
- **§36 — the macOS app no longer crashes (SIGSEGV) rendering the Planning Aladin atlas.** CEF 130's renderer was forced **in-process**, and Chromium 130's Rust `fontations` font backend segfaults on certain glyphs — so the whole app died (`Chrome_InProcUtilityThread` → `fontations_ffi…`) instead of, at worst, a recoverable renderer. The `webview_cef` submodule is bumped to the fork's multi-process build (helper-bundle model + the `fontations` workaround) and the **helper subprocess target(s) are wired into the macOS Runner** so CEF runs its renderer/GPU/utility work out-of-process (the stable, default Chromium model). The host gains the JIT / `disable-library-validation` entitlements CEF requires to load its separately-signed framework. (This later moved to CEF 149 with the full five-helper set and the App Sandbox turned off — see the CEF 149 entries above; `disable-library-validation` keeps distribution to Developer-ID / direct, not Mac App Store, which is how CEF apps ship.)
- **§26 — a clean `Debug` build of the daemon no longer fails on current .NET SDKs.** `InvariantGlobalization` was set only in the `Release` configuration, so a Debug build ran with the machine's locale active. Under a newer SDK's analyzer set (10.0.3xx) that turns the whole CA13xx locale-sensitivity family (CA1305/CA1307/CA1308/CA1310 — `IFormatProvider`/`StringComparison`/`ToLowerInvariant`) into build-breaking errors for ~59 `Sqlite*`/parse call sites in the Server project, so `dotnet build -c Debug` failed on those SDKs even though `Release` (and CI, which builds Release) stayed green. The daemon only ever speaks invariant/wire formats (ISO-8601 timestamps, snake_case keys, numeric REST values), so `InvariantGlobalization=true` now applies to **every** configuration: a Debug build behaves identically to the shipped daemon (no machine-locale date/number parsing skew in dev) and the analyzers correctly stand down in Debug too. Root-cause fix — no per-call-site `IFormatProvider` churn, no Debug/Release globalization divergence.
- **§36/§25.5 — the camera/sensor FOV box now draws when framing in Planning.** Frame mode's FOV overlay (and the whole optics-derived framing) silently showed nothing because the Planning tab never loaded the profile's optics — only **Settings → Optics** ever hydrated `opticsSettingsProvider`, so in a Planning-only session it held the zero default, `frameFovBoxProvider` returned null, and the camera's sensor size never appeared on the atlas. The Planning tab now hydrates the profile's optics (focal length + sensor size + pixel scale) from the daemon on mount, so the FOV rectangle/mosaic draws from the user's actual camera + scope. (The FOV math, overlay JS, and framing controls were already complete — only the load was missing.)
- **§25.3 — the top-bar equipment icons are now live + clickable (all devices, not just the guider).** The app-shell equipment status row (CAM / FW / FOC / MOUNT / ROT / FLAT / SW / WX / SAFE / DOME) was hardcoded to a grey "disconnected" dot with no tap handler — only the GUIDE chip was wired — so connecting equipment via AlpacaBridge showed no green dot and the icons did nothing. Each chip now watches its device's live status provider (added by the §25.5 conformance work) and shows a green dot when connected (amber while a move/op is in flight, blue while connecting, red on error), and tapping any chip jumps to that device's **Settings → Options** panel to connect/control it — mirroring how the guider chip already worked. Switch is handled as multi-instance (connected if any switch is); the flat panel has no live status feed yet, so it stays grey but is clickable to its panel.
- **§37 — finishing the wizard "saved" a profile that never appeared.** Tapping **Save Profile** / **Save & Exit** created and activated the profile on the daemon (verified: the file-based store writes atomically), but the wizard only refreshed the client's cached profile list when launched from the Profile-management screen — **not** from the app-shell "Run profile wizard" launcher or the Settings "Open wizard" panel (those passed no `onComplete`). So the save succeeded, the wizard closed, and the stale list made it look like nothing was saved. The wizard now invalidates the profile-list cache itself on a successful save, so the new profile shows up regardless of where the wizard was opened from.
- **§6.4/§37.2 — the wizard can now discover + assign a Switch device.** The equipment-assign screen (Screen 3) showed the **Switch** slot greyed-out with "Multi-switch support is in progress (§6.4)" and no **Choose** button, so a user couldn't pick a switch during initial profile setup. Now that multi-switch is wired end-to-end, Switch discovers and assigns exactly like every other Alpaca slot (it maps to the daemon's `discover/switch` endpoint). The wizard assigns one switch as the profile's default; additional switches are added at runtime from **Settings → Switch**. (Also generalizes the slot model — every slot is now discoverable, removing the special-cased non-discoverable branch.)
- **§70.5 — sequence share-export returned a bogus placeholder for unknown ids + advertised a dead download route (server).** `POST /api/v1/sequences/{id}/share-export` synthesized an empty "Unknown sequence" share (body `{}`) for an id that doesn't exist instead of the `404` the endpoint already advertised, so exporting a deleted sequence looked like it succeeded. It also populated `SequenceShareDto.DownloadUrl` with a `/share/payload` route that was never implemented — diverging from the profile-share contract, where the share JSON rides inline in `Manifest` (the client writes it straight to the chosen `.araseq.json` file) and `DownloadUrl` is null. `ShareExportAsync` now returns null → `404` for an unknown id, and the DTO mirrors `ProfileShareDto` (`DownloadUrl` nullable, null in v0.0.1; `PayloadBytes` is the inline manifest's UTF-8 byte size). Client export UI is the next slice.
- **§6 — the Switch panel stayed stuck on "Connecting" after Add switch (client).** The daemon's switch connect is 202-accepted + runs in the background, so a freshly-added switch first reads back as `connecting`; the panel re-read the list once right after the connect and then never again (the provider is pull-on-demand), so the card sat on **Connecting** until the user re-opened the panel — looking like the connect failed even though the daemon had connected. The panel now polls (1.5 s, no-op when nothing is connecting) while any switch is mid-connect, so a card settles to its real state on its own. (Verified end-to-end against a live AlpacaBridge: both an iOptron iMate PowerBox and a Player One thermal switch connect and report their ports.)
- **§6 — equipment discovery parsed every device to blanks (client).** `DiscoveredDevice.fromJson` read **camelCase** keys (`uniqueId`, `hostName`, `alpacaDeviceNumber`, …) with a comment claiming the daemon emitted camelCase, but the daemon serializes with `SnakeCaseLower` (so the wire is `unique_id`, `host_name`, `alpaca_device_number`, …). Every discovered device therefore came back with a blank name + empty `uniqueId` + device number `0`, breaking the whole discover→select→connect flow for **all** equipment types (the chooser showed nameless rows; a "connection" pointed at a default device). Now reads snake_case (with a camelCase fallback so either shape parses), with a model test pinning the daemon's real wire shape. This was the prerequisite blocking connecting Switch (and other) devices from the client.
- **§29.9 — `GET /api/v1/server/logs/download` no longer 500s on the active log.** The download streamed the live log file while the Serilog sink kept appending to it; `Results.Stream` set `Content-Length` from the file size at open time, so the copy ran past that length (the file grew mid-flight) and Kestrel aborted with `Response Content-Length mismatch: too many bytes written`. The download now serves a snapshot capped to the file's length at open (a small `LengthCappedStream` over the `FileStream`), so `Content-Length` matches the bytes sent and the response completes. This is what surfaced as "Download daemon log" failing in the Support tab.
- **§54 — the in-app daemon log viewer is now selectable/copyable (client).** The Support-tab log rows were plain `Text` widgets, so a user couldn't select or copy a log excerpt. The list is now wrapped in a `SelectionArea`, enabling drag-select across rows and copy (Cmd/Ctrl+C) — so a user can paste a snippet into a bug report without downloading the whole file.
- **§54 — the macOS client can save downloads again (Download daemon log / bug-report bundle).** The sandboxed macOS app was missing the `com.apple.security.files.user-selected.read-write` entitlement, so writing the file the user picked in the save dialog failed with `PlatformException(ENTITLEMENT_REQUIRED_WRITE)`. The entitlement is now granted in both `DebugProfile.entitlements` and `Release.entitlements`, so the OS save dialog can write to the chosen location.
- **§38 — the sequencer toolbar no longer offers an inoperative Pause control.** The daemon's sequence `PauseAsync` is an accepted no-op — the headless execution engine has no pause hook yet, so it deliberately never suspends a run or emits a `paused` event. The toolbar nonetheless showed an enabled **Pause** button (and a dead Run→Resume relabel) while a run was active, so clicking it returned `202 Accepted` but did nothing, with the run-state never reporting `Paused` — misleading the user into thinking the run had paused. Pause/Resume are now removed from the toolbar until the engine grows real run suspension; Run / Abort are unchanged. The run-state model (including the `paused`/`Paused` state) is retained so Pause/Resume can be re-surfaced wholesale when the daemon supports it.
