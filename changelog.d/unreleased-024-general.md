### Added
- **Update the server from the client with no internet (§33).** At a dark site apt can't reach the archive, so the rig had no way to take an update. The daemon now accepts a pushed `openastroara-server` `.deb` (`POST /api/v1/server/update`, then `/{id}/apply`): it checks the package name, architecture, that it is newer than what's installed, and an optional SHA-256, then hands it to a root helper unit that installs it, restarts the daemon, and **rolls back to the previous version automatically** if the new one doesn't come up healthy within 90 s. Clients get a `server.restart_imminent` event first and can read the outcome after the restart (`GET /api/v1/server/update/{id}`). Escalation is a polkit-scoped systemd oneshot like the storage helper — the daemon itself never gains privileges — and the dead `update.sh` sudoers line is gone. The client button that drives this is separate work. (#1122)

### Fixed
- **The published API spec matches the daemon again.** `OpenAstroAra.Server/openapi.yaml` had frozen at 28 hand-written paths (several of them long gone) against ~200 live routes. It is now a snapshot of the OpenAPI document the daemon already serves at `/openapi/v1.json` (titled "OpenAstro Ara REST API" in the `/scalar` docs page), and a test fails CI when a route changes without the snapshot being refreshed. The WebSocket protocol notes the old file carried moved to `design/API_CONTRACT.md`. (#1131)
- **The automated meridian flip actually slews.** The daemon's flip call was a stub that reported failure, so every §58 flip ended in the fail-safe (mount in safe rest, run paused awaiting the user) even once the trigger fired at the right time. The flip now does what NINA's does: when the profile uses side of pier and the mount can set it, command the side the target belongs on, then an ordinary goto to the same target (a mount past the meridian lands on the other side on its own), and refresh the mount snapshot so the post-flip verification reads the new side. A mount that reports it does not implement side of pier is asked once instead of every two seconds. (#1238)
- **Storage helper housekeeping.** A storage request cancelled mid-configure could leave its `<id>.result` in the daemon's tmpfs exchange directory until reboot; the daemon now sweeps stale `*.request`/`*.result` files at startup. Two storage operations landing together could clobber each other's `/etc/fstab` rebuild through a shared temp name; the rebuild now runs under a lock with a per-call temp file. The helper's paths are injectable and the wrapper honours `DIR`/`HELPER` overrides, so the request/result round trip (argv rebuild, the argument cap, the non-regular-file refusal) is covered by tests against the real wrapper script. (#1135)
- **A mount that AlpacaBridge has latched as "Mount communications compromised" recovers on its own.** After a mount Wi-Fi blip the bridge keeps answering "connected" while every position read fails with that message, so the daemon's disconnect detection never fired and the mount stayed faulted until someone disconnected and reconnected it by hand. The 2 s refresh now recognises the latched error, marks the mount Error with a fault-log entry that says what happened, and hands it to the §42.3 reconnect ladder (bounded retries, the running sequence paused meanwhile and resumed on recovery, a notification and the card's state) — never while a slew is in flight, and once per fault episode rather than on every tick while the bridge stays latched. (#1193)
- **Equipment card Reconnect/Remove follow-ups.** Reconnect on a device card dispatched the *remembered* auto-connect entry, which can be gone (the wizard's store-only forget) while the daemon still holds the device the card names; it now falls back to that retained device instead of answering "no previous device". Removing a device now tells every connected client (an `equipment.state_changed` with `removed: true`), so a second open client drops the card at once. A switch mid-connect no longer offers Remove (the daemon refuses it, as it does a connected one), and removing a switch that tripped to Error releases its driver connection instead of leaking it. A removal racing the daemon's shutdown is reported as a server error rather than "disconnect first". (#1127)
- **A guide-camera drop's fault-log row closes when the camera comes back, not on the next guider connect.** The guider's `EquipmentReconnected` event was parsed but only logged, so a camera that dropped and recovered mid-session (guider link up the whole time) left its fault row unresolved until the guider itself was reconnected. The reconnect now resolves exactly that row (the §42.3 action stamp is kept) and posts an Info notification that guiding can resume; the on_guider_lost reaction stays one-shot per connect, so a flapping camera still cannot pause, skip or abort a run on every cycle. (#1191)
- **A sequence with a meridian-flip trigger no longer tries to flip at its first item boundary.** The daemon's mount snapshot left the time-to-flip and sidereal time at 0 and the pier side at "east" (it never read them), and the flip trigger reads 0 h as "the flip window is now", so on any tracking mount with a known position the trigger fired before the first instruction, the flip failed and the run paused awaiting the user. The snapshot now carries the local sidereal time from the profile's site longitude, the time to flip from the same meridian rule the trigger expects (including the side-of-pier 12 h deferrals), and the mount's reported pier side (unknown when it cannot say, which the post-flip verification no longer mistakes for "did not move"). Anything that cannot be computed (no site, no position) is reported as unknown, which the trigger skips with a warning rather than acting on. The same sidereal time now feeds polar alignment's RA seed-slew direction, which previously computed it from a sidereal time of 0. (#1229)
- **Guider recovery stays on the guider that dropped, and a remote guider never triggers a local `systemctl start`.** Auto-reconnect after a guider link loss read the host and port from whichever profile was active when recovery landed, so switching profiles mid-recovery "recovered" by connecting to the new profile's guider (and wrote the old target into it). The pass now pins the host:port and profile that were live at the drop, re-checks them before every attempt, and abandons with a log line when they changed, leaving the guider in Error for the new profile's own connect. Separately, an unreachable guider on connect always asked systemd to start the local `openastro-guider` unit, even when the profile points at a guider on another machine; the start, the crash-recovery tree and the guider restart action (`POST /api/v1/equipment/guider/restart`) now run only when the configured host is this machine (loopback, its host name or one of its addresses) — a remote guider gets a "Guider connection lost" notification and a plain reconnect within the retry window instead. (#1192)
- **The mount's direction pad works out of the box on a single-rate mount, and a slow diagonal press moves both axes.** The daemon published only the endpoints of each axis's MoveAxis rate bands, so the client could not tell "any speed up to 6°/s" from "6°/s only": on a fixed-rate mount it built percentage presets and defaulted to one the daemon then refused (409), leaving the pad dead until a chip was tapped. The capabilities now also carry the bands themselves (`move_axis_rate_bands_deg_per_sec`, `[{min, max}]`; a fixed step has `min == max`), the speed chips are built from them (a fixed-rate mount shows exactly its steps, a continuous band keeps the percentage presets), and the offered bands are clipped to the secondary axis's floor as well as its ceiling, so a corner press on a mount whose N/S axis is slower than E/W no longer moves one axis and refuses the other. The manual-move help no longer talks about multiples of sidereal. The old endpoint list stays on the wire for older clients. (#1126)
