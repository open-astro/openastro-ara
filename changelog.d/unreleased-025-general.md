### Added

The app now records every framework error and uncaught async error to `client-errors.log` in its app-support folder (capped at 512 KiB with one rotation, each entry carrying the last 200 console lines), and the Support tab gains "Save client log" above the connect gate so it works with no rig reachable. "Send me a bug report" saves the client log beside the ZIP, and Help → Copy diagnostics includes a one-line summary. Release builds show a compact fallback in place of a broken widget instead of Flutter's grey box. (#1111)

Frees a USB port on the Pi for gear; you are next to the mount during setup and polar alignment, so the fix is the rig's. Desktop (macOS, Windows, Linux) only — phones and tablets keep using their built-in GPS.

- **Android and iOS clients.** The Flutter client now carries `android/` and `ios/` platform folders (`org.openastro.openastroara`) with the permissions the daemon connection, mDNS discovery and geolocation need, and side-loads onto a Pixel Tablet and an iPad. Every platform's launcher icon is generated from one source with `flutter_launcher_icons`: iOS gets a full-bleed square, Android an adaptive icon whose constellation floats on a seamless star field, macOS/Windows keep the rounded artwork. Store distribution stays deferred (release builds are debug-signed; no Android/iOS CI leg yet).
- **XISF headers name OpenAstro Ara and declare their block alignment.** `XISF:CreatorApplication` (and the log banner) now say "OpenAstro Ara" instead of N.I.N.A.; the writer emits `pixelStorage="Planar"` explicitly and an `XISF:BlockAlignmentSize` metadata property with the alignment it actually uses (1024), which readers honouring the spec default of 4096 need to be told. The HTTP `User-Agent` string names OpenAstroAra instead of N.I.N.A. and reports the real OS and process architecture rather than Windows bitness.

Decompression is bounded by the declared uncompressed size, so an oversized frame is rejected rather than grown.

First step of #996.

- **Six add-on deep-sky catalogs.** Sharpless HII regions (313), Lynds dark nebulae (1,787), Barnard dark objects (349), van den Bergh reflection nebulae (158), Abell planetary nebulae (86), and Arp peculiar galaxies (338) — commit-pinned in `open-astro/sky-data`, SHA-verified, normalized to the OpenNGC layout. ### Fixed
- **A Reconnect Equipment trigger no longer fails a run over a PHD2 socket drop.** When the guider link drops, the daemon already recovers PHD2 and reconnects within the profile's guider retry timeout, but the trigger fired in that window and failed the run at once (the guider's sequencer connect did nothing). The trigger now waits for that recovery, up to the retry timeout, and the run continues if the guider comes back. If the host has no systemd guider unit, it reconnects the guider itself. If nothing reconnects in time, the trigger fails as before and the recovery keeps running. The sequencer's Connect Equipment and Disconnect Equipment instructions now work for the guider too. (#1123)
- **Start Guiding with Force Calibration no longer shows a false "guider cannot clear calibration" warning.** The daemon's guider reported that it could not clear calibration, although PHD2 can. It now reports the real value while connected. (#1123)
- **The meridian-flip trigger no longer crashes on a mount that hasn't reported a position.** `MeridianFlipTrigger.ShouldTrigger` dereferenced the telescope's coordinates for the same-target dedup distance and the side-of-pier projection without a null check; before the first position read (and, since #1220, for the whole session on a mount whose `EquatorialSystem` can't be read) that threw `NullReferenceException` on every evaluation. An unknown position is now treated like "not tracking": the evaluation is skipped with a warning and no flip fires. (#1221)
- **A restart with the frames disk ejected reports "store ejected", not a permission error.** Since the store path became an optional `ReadWritePaths=` entry (#1186), a daemon started while `/media/openastroara` exists but no disk is mounted sees systemd's bind of the empty directory as a mount line backed by the root filesystem, so the pre-capture gate and the device watcher called the store "mounted" and a capture failed writing to the root-owned directory. The store now counts as mounted only when the mount's source device differs from its parent filesystem's, which a bind never does and a real exFAT/ext4 USB disk always does. (#1207)
- **Sidereal time and topocentric transforms carry the real UT1-UTC offset.** DUT1 had been stubbed to 0 since the port dropped NINA's earth-rotation SQLite table, so LST, hour angle and every altitude/azimuth the daemon computed were off by up to 0.9 s of UT1 (about 13 arcseconds of hour angle). The daemon now embeds a snapshot of the IERS Bulletin A daily series (`OpenAstroAra.Astrometry/External/iers-dut1.tsv`: 2024-01-01 through the bulletin's year of predictions) and interpolates it by date, with no network needed at the site. A date past the table's end extends it with Bulletin A's long-term formula for a year, then holds (always within the +/-0.9 s DUT1 bound, logged once); `OPENASTROARA_DUT1_TABLE` points the daemon at a newer file, and `scripts/update-dut1-table.py` refreshes the snapshot before a release. (#1190)
- **A frame shot within half a second of RA 24h keeps its coordinates.** The sexagesimal formatters rounded 23:59:59.96 up to `24:00:00` (and 359° 59′ 59.96″ up to `360° 00′ 00″`), so the capture path wrote an `OBJCTRA` card the frame scanner rejects and the frame lost its near-solve hint. `HoursToHMS`/`DegreesToHMS` now wrap to `00:00:00` and `DegreesToDMS` to `00° 00′ 00″` when rounding carries into the wrap point; the pole still reads `90° 00′ 00″`, and ordinary values format as before. (#1125)
- **A chatty plate solver no longer stalls until the 10-minute timeout.** The CLI solvers (ASTAP and the other command-line solvers) redirected the solver's stdout but never read it, so a solver that printed more than the 64 KB pipe buffer blocked on write until the solve timed out, and its output never reached the log or the solve status. Both stdout and stderr are now read as the solver runs and drained before the result is read. Each line is logged at Debug (stderr used to be Error, which would have made every progress line an error) and shown as the solve's status; when the solver exits non-zero, the exit-code warning carries its last 20 lines. (#1188)
- **A slew or sync right after connecting the mount no longer lands ~0.36° off.** Until the daemon had read the mount's coordinate system (`EquatorialSystem`), it assumed JNOW, so a sequence slew or a centering sync issued before the first status read precessed a J2000 target the wrong way for a J2000 mount. A slew or sync in that window now reads the coordinate system first (bounded to 10 s); if the mount still doesn't answer, the slew fails the instruction with a clear error and the sync reports "not synced" (centering offset-compensates) instead of sending coordinates in a guessed frame. Frames captured while the coordinate system is still unknown carry no RA/DEC/EQUINOX pointing rather than a mislabelled one. (#1124)
- **Settings → Plate solving says whether the rig has a star database.** A fresh install that skipped the DEPLOY.md star-database step failed every solve with ASTAP exit 32, and only the daemon log said why. The panel now shows "N files found in <path>" (with the databases found, e.g. D80), a "No star database" warning that points at the install step, or "Unknown" when offline or on an older daemon, plus a line when the solver binary is missing (new read-only `GET /api/v1/platesolve/database`). A profile from before #1094 that still points at `/usr/bin/astap` moves to `/usr/bin/astap_cli` when only the latter is installed, and the daemon logs a boot warning when the configured solver binary is missing. With more than one star database installed, the daemon now names one with `-D` instead of leaving ASTAP to choose: fields narrower than 0.25° take the deepest (H18, H17, then D80), fields wider than 30° the shallowest (W08, G05, D05), and everything else D80 first. (#1121)
- **A missing CFITSIO shows at boot, not at the first exposure.** The daemon now loads CFITSIO while it starts and logs where it came from (`CFITSIO loaded from libcfitsio.so.10`), or, when nothing loads, an error with the install hint (`sudo apt install libcfitsio10` on the SBC) and every candidate it tried. It keeps running either way. `OPENASTROARA_CFITSIO_PATH`, documented but never read, now works: set it to the full path of the library file and it is tried first, before the default search and the `libcfitsio.so.10` fallback. The `libcfitsio.so.9` fallback is gone (Debian 11 and Ubuntu 22.04 are not targets). On the Linux CI runner the FITS tests now fail when CFITSIO does not load instead of passing with nothing exercised. (#1120)
- **A fresh install starts before any frames disk is set up.** The server unit listed `/media/openastroara` as a required `ReadWritePaths=` entry, but only the storage step creates that directory, so on a new SBC systemd could not build the service's mount namespace and the daemon restart-looped with `226/NAMESPACE` until a disk was attached by hand. The entry is now optional (`-/media/openastroara`): a fresh install starts with no disk, and a disk attached later from the app is writable without a restart. Rigs that already have the directory are unchanged. A new `scripts/tests` check fails the build if a required `ReadWritePaths=` entry is not created by the package. (#1186)
- **The sequencer's Cool Camera and Warm Camera instructions work, and so do dark libraries built at a set temperature.** Both were stubs on the daemon's camera: Cool Camera always failed with "could not reach target temperature" (so every temperature-set dark library failed at its first step, as did imported NINA plans that cool), and Warm Camera did nothing. The camera also never reported that it could take a set-point, so both instructions failed validation before running. Cool Camera now writes the set-point at once (duration 0) or ramps it along a straight line in 15 s steps over the duration, then waits for the sensor to get within 1 °C of the target. It fails with the reason when the camera cannot take a set-point, the cooling fan cannot start, or the sensor makes no progress for 2 minutes with the cooler saturated (10 minutes while the cooler still has headroom). Warm Camera ramps toward 20 °C, pauses 20 s and switches the cooler off; a cold night that stops it short of 20 °C still ends with the cooler off, and a cooler that is already off is never switched on. Cancelling holds the set-point at the current sensor temperature. Every write goes through the same path as the cooler control, so the cooling-fan interlock (#1076) covers sequences too. (#1187)
- **A release build blocked by macOS Local Network privacy now says so instead of never finding the rig.** The connect screen's mDNS query is a raw multicast send, and when macOS refuses it (a denied or unanswered "Local Network" prompt, which a Finder-launched app gets and a terminal-launched debug app inherits from the terminal) `dart:io` reports the failure asynchronously on the socket stream. The client never registered a handler for that stream, so the failure was an unhandled error and every discovery pass came back empty while `dns-sd -B` on the same Mac saw the rig. The error is now caught and logged (`[discovery] mDNS socket error: …`), and while it is happening the connect screen shows a banner with the fix (System Settings → Privacy & Security → Local Network, then ⟳); manual add keeps working. (#1111)
- **The client's root widget tree holds still.** Four things used to rebuild, reparent or remount large parts of the app for no visible reason: every "GPS on this computer" sync rebuilt `MaterialApp` with a fresh theme; toggling night mode moved the whole Navigator to a new parent; every slew start, stop, abort or link drop tore down and re-inflated the entire shell (toolbar, tab stack, every visited tab, the planetarium); and a planetarium page event could look up the snackbar host after the view was disposed. The root is now a stateless widget with one shared theme, night mode is a fixed render-layer filter above the Navigator, the Stop Mount overlay keeps the shell in place and only adds its banner, and the page-event handler checks it is still mounted. Removes every avoidable rebuild hazard around the "check that it really is our descendant" red screen seen on a Live → Planning switch. (#1111)
- **The planetarium no longer polls the rig's site every 2 seconds.** With the Planning tab open the page fetched the profile site 30 times a minute for the whole session; this client's own site edits already reach the page instantly from Dart, so the poll now runs every 30 s as a net for edits made on another client. (#1111)
- **mDNS discovery failures are logged.** The connect screen's multicast browse swallowed every exception, so a release build that never listed a rig `dns-sd -B` could see gave nothing to go on. Browse and address-lookup failures now print a `[discovery]` line to the console. (#1111)
- **Attaching, checking, reformatting and ejecting the frames disk works on a packaged Pi.** Every storage action failed with "sudo: The \"no new privileges\" flag is set" because the daemon's hardened unit forbids privilege escalation, so its sudo-based helper call could never run. The .deb now ships a root-owned `openastroara-storage@.service` template plus a polkit rule scoped to it; the daemon writes a request file, asks systemd to start one instance, and reads the helper's result back, holding no privilege of its own (the same pattern as guider unit control). Existing installs pick it up on the next package upgrade.
- **Captures work on a stock Pi install.** Every exposure on a packaged install failed at the FITS write with `DllNotFoundException: Unable to load shared library 'cfitsio'`: the .deb depends on the `libcfitsio10` runtime package, which ships only `libcfitsio.so.10`, while the daemon probed for the bare `libcfitsio.so` that only the `-dev` package provides. The server now falls back to the versioned soname itself, so no development package is needed on the SBC, and CI installs the runtime package only so it exercises the same path as the Pi.
- **Every equipment card keeps a disconnected device and offers Connect and Remove.** Camera, mount, focuser, filter wheel, rotator, dome, flat panel, weather station and safety monitor cards used to collapse to an anonymous "No … connected." row after a disconnect. They now keep the device's card with a Connect icon (reconnects that device, no chooser) and a Remove icon that drops it and stops it auto-connecting on boot, matching the Switches panel; Connect… still picks a different device. Backed by a new `DELETE /api/v1/equipment/{type}` (409 while the device is connected — disconnect first).
- **A disconnected switch can be reconnected from its card.** The Switches panel card offered only Disconnect whatever the switch's state, so a switch you disconnected had no way back on its own card: the header Reconnect appears only when every switch is down, and the other path was re-picking the device through Add switch. The card now shows Connect while the switch is disconnected or in error, backed by a new per-switch `POST /api/v1/equipment/switch/{id}/connect` that reconnects from the discovery record the daemon already holds (a 404 — the daemon no longer knows the switch — points you at Add switch).
- **Equipment auto-detect works on a packaged Pi.** The daemon's systemd hardening allowed only IPv4/IPv6/Unix sockets, but .NET lists network interfaces over a netlink socket on Linux and the Alpaca discovery library does that before every broadcast, so every `GET /api/v1/equipment/discover/{type}` failed with "Address family not supported by protocol" and the setup wizard's AlpacaBridge auto-detect could never succeed on a real install. The unit now also allows `AF_NETLINK`. Existing installs pick it up on the next package upgrade (or add a drop-in with `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX AF_NETLINK`).
- **Plate solving works on a fresh Pi install.** Nothing installed ASTAP: the `.deb` did not depend on it, the profile pointed at `/usr/bin/astap` (Debian's package installs `/usr/bin/astap_cli`), and the solver never told ASTAP where the star database was, so polar alignment and centering could not solve at all. The package now depends on Debian's `astap-cli`, the default path is `/usr/bin/astap_cli`, the profile's index path is passed to `astap_cli` as `-d` (a configured directory that is missing or empty logs one warning per daemon run and falls back to ASTAP's own lookup), and DEPLOY.md gains the one-time D80 star-database download.
- **Guider supervision talks to the unit that actually exists, and aggressiveness reaches the guider.** Verified against a Pi running openastro-guider 2.1.0: the daemon supervised a systemd unit named `openastro-phd2`, but the guider .deb ships `openastro-guider.service`, so crash recovery and Options → Guider → Restart nudged a unit that does not exist (`is-active` on a missing unit prints `inactive`, so it looked like a stopped guider rather than a wrong name). Now that supervision reaches the real unit, a deliberate `systemctl stop openastro-guider` by an admin mid-session will be met with a restart request from the daemon's recovery loop; that interplay is tracked as a follow-up. The unit name is corrected, and the .deb now ships a polkit rule that lets the service user start/restart exactly that unit over D-Bus (the daemon runs under `NoNewPrivileges`, so a sudo rule would not work — verified on the Pi). Separately, the §63.5 settings push sent RA/Dec `aggressiveness`, a parameter PHD2 does not have (its name is `aggression`), so those two values were rejected on every connect ("could not set param"); the wire name now matches the daemon and the push lands all four algorithm parameters once a mount is selected.
- **The Pi package ships the astrometry natives.** The SOFA and NOVAS31 libraries were only ever built for the CI test job, never staged into the published daemon, so a real install had no `libsofa.so` / `libnovas31.so`: slews quietly used untransformed coordinates, and altitude/sun/moon conditions, the meridian-flip projection and polar-align solving would have faulted on first use. CI now cross-compiles them for linux-arm64 into the publish directory (Docker image and `.deb` both carry them), `build-deb.sh` refuses a publish tree without them, and the daemon logs `Astrometry natives loaded` or an `Astrometry natives incomplete` warning in its first lines.
- **Frames carry where the mount was pointed.** Lights (and every other frame taken with a mount connected) now get `OBJCTRA`/`OBJCTDEC` (sexagesimal), `RA`/`DEC` (degrees) and `EQUINOX` from the mount's position at readout, converted to J2000. Before, no capture path wrote pointing at all, so the §18.I solve-from-header hint never fired and stackers had no target grouping on manually framed lights. If the astrometry natives are missing the cards carry the mount's own epoch and `EQUINOX` says so instead of claiming 2000.0.
- **Plate-solve centering can take its exposure.** The daemon's capture seam for the solve loop still threw "not ported", so every centering path — the `CenterAndRotate` sequence step, `POST /api/v1/platesolve/center`, the meridian flip's recenter and the safety re-center — failed on its first exposure. The capture now rides the same unpersisted expose/download core the autofocus probe uses, hands the raw 16-bit frame to the solver, and renders the progress thumbnail with the §65 AutoSTF stretch. Solve frames are still never catalogued.
- **Sequences guide and dither again.** The daemon still wired the sequencer's guider seam to the headless no-op stub. `StartGuiding` failed loudly ("Failed to start guiding"), but `StopGuiding`, `Dither` and `DitherAfterExposures` discarded the stub's `false` and reported success, and the meridian flip skipped its guide pause/resume as "guider not connected" — so a run that got past Start Guiding was undithered, and a flip never resumed guiding. The real `GuiderService` now backs the mediator, as its own comment already claimed.
- **Rig discovery no longer misses a daemon at a high address when mDNS is empty.** The connect screen restarts discovery every ~4 s and the restart cancelled the subnet sweep before its last batches ran, so on Android (where the raw-socket mDNS browse never answers) a daemon at e.g. `.235` was never probed. The sweep is now shared across passes and a just-finished sweep replays its hits; joining never spawns a new sweep, an mDNS answer drops the sweep path, and ⟳ Rescan forgets the cache so a daemon that went away is re-probed rather than replayed. "Fill from GPS" failure copy is mobile-aware too: a tablet that denies the location prompt is no longer told to plug a GPS dongle into a Linux machine.
- **XISF reader honours `bounds` and validates `pixelStorage`/`colorSpace`; multi-channel files are a clear error.** Float samples are mapped through the file's declared `bounds="lo:hi"` (the spec makes it mandatory for float formats) instead of assuming [0, 1]; `pixelStorage` and `colorSpace` outside the spec vocabulary, a malformed `bounds` on a floating-point format (on an integer format `bounds` is ignored, as the spec says, so a junk value there no longer makes the file unreadable), and a truncated `compression` or `checksum` attribute are all `InvalidDataException` rather than an index exception escaping the loader. A 3-channel RGB file now fails with a message saying so instead of being handed to a single-channel image as a scrambled 3×W×H array (colour support remains under #996).
- **32-bit XISF written by Ara now reads back as the same ADU.** `SaveXisf` wrote raw ADU into a `sampleFormat="UInt32"` block whose spec range is [0, 2^32-1], so a spec-correct reader (ours since the previous entry, and PixInsight) saw ~0 everywhere. Values are now scaled by the camera bit depth onto the full range; a 16-bit camera round-trips exactly. The writer also stages the header and padding in memory, so an inconsistency throws before anything is written to the file.
- **XISF files are read to the spec's sample mapping and refuse corrupt blocks.** `UInt32` and `UInt64` samples were scaled by the *signed* maximum, so any sample above half scale wrapped negative and read as garbage; `Float32`/`Float64` samples were neither clamped nor NaN-checked. All four converters now map the spec's full range onto 16 bits with rounding, and floats clamp to [0, 1] with NaN reading as 0. A block that fails its declared checksum is rejected with an error instead of a warning-and-continue (design/AUDIT.MD #H3), on inline and embedded blocks as well as attached ones; previously inline blocks were neither verified nor decompressed. Inline blocks are read from the `Image` element's own text per XISF 1.0 (`inline:base64` and `inline:hex`), `embedded` blocks from the `Data` child, and the legacy child-`Data`-under-inline layout is still accepted. An unsupported sample format (`Complex32`, `Int16`, …) or codec (`bzip2`, say) is a clear error, not a garbage image. The reader now fills `ImageType` from the `imageType` attribute or `IMAGETYP`.
- **XISF writer can no longer declare a data block that overlaps its own header.** The attachment offset assumed the location/compression/checksum attributes fit in 256 bytes; it is now found by fixed-point iteration on the serialized header length, and `Save` refuses a negative padding rather than writing an unreadable file. `SWCREATE` names OpenAstro Ara instead of N.I.N.A., and choosing a SHA-3 checksum on a platform without SHA-3 (macOS) falls back to SHA-2 with a logged warning instead of failing the save.
- **A switch whose hardware link dies now reads as disconnected instead of "Connected" with an empty card.** Ara's §42.3 disconnect detection trusted the Alpaca `Connected` property as its only proof of life, but a bridge may implement `Connected` as **per-client session state** (our session stays connected no matter what the hardware is doing) and a driver may keep serving static metadata — `MaxSwitch`, `GetSwitchName` — from a table while the link to the device is dead. Seen on a Gemini Power & Data Hub ADV3 after a USB replug: `Connected` true, `MaxSwitch` 24, and every `GetSwitchValue` throwing "communications compromised", so the daemon held the switch at `Connected` indefinitely while the panel showed "No ports reported by this switch" and nothing ever offered to reconnect. A device that advertises ports but delivers none now counts as a failed probe on its own, deliberately longer streak — ten consecutive unreadable reads, ≈20 s, plus two grace observations a connection gets once before they start counting, so a USB re-enumeration or an isolated bad read isn't held against it. That is separate from the existing `Connected` probe, which still trips after three failures; the §42.2 fault event now names whichever detector actually fired instead of always claiming three connection probes. Verified against the real hardware in that exact state.
- **2026-08-10 (UTC) — mount manual slew gets slew-speed percentage buttons.** The direction pad's speed picker only offered rates the mount reports; the ZWO AM5N reports a single max rate (6.016 °/s), so every nudge lurched at full speed. - **2026-08-10 (UTC) — daemon: a parked mount can never read as "slewing" (phantom-motion guard).** `TelescopeService.ReadRuntime` now resolves the runtime-state token via `ResolveRuntimeState`, where `AtPark` is a definite rest state that **wins over `Slewing`** — a driver/bridge reporting `Slewing == true` while `AtPark == true` is lying or stale (a parked mount cannot be moving). Observed in the wild: the AlpacaBridge ZWO vendor reported `connected/slewing/tracking/atpark` all true with no mount attached, painting "Mount is Slewing" in the UI while the mount sat still. The guard makes a buggy/phantom device (new, old, or any vendor) unable to display motion on a parked mount. Unit-tested (`TelescopeRuntimeStateTest`, 7 precedence cases).
- **2026-08-10 (UTC) — wizard: bridge handshake reports reachability, not a phantom device count.** Screen 2's success copy said "N camera(s) seen on this scan" whenever discovery returned *any* advertised slot — even a registered-but-absent device (a vendor slot with no hardware behind it), which the AlpacaBridge advertises by name with `/connected == false`.
